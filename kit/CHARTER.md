## Project docs charter

**Precedence:** the owner's live instruction > active spec in `docs/specs/` > `docs/DECISIONS.md` > other docs. If an instruction contradicts a decision, follow the instruction, name the conflict in one line and log a new decision. Decisions tagged `[model]` change only with their author.

**Before work:** read `docs/STATE.md` and `docs/TODO.md`. Before product, architecture, data or deploy decisions, also read `docs/CONTEXT.md` and the relevant `docs/DECISIONS.md` entries. Before touching fragile code, read `docs/PITFALLS.md`. Before any UI change, read the project's design system doc named in `AGENTS.md`; sizes, spacing and colors come from its roles and tokens, not from the eye.

**Claims:** before editing, run `agentdrop status` (what waits for the owner, what other sessions hold, what's next) and claim your ticket: `agentdrop claim B<n>`. If another session holds it, take another ticket or ask the owner; never work on a claimed ticket silently. A pass without a ticket (docs, review intake) claims nothing but still checks status for sessions editing the same docs. Release at the end of the pass, also when you stop halfway: `agentdrop release B<n>`.

**Tasks in the store:** `agentdrop task where` says where this project's tasks live. If it says the store, the store replaces `docs/TODO.md` and `docs/QUESTIONS.md` wherever this charter names them: never read or edit those two files. `agentdrop task take [B<n>]` claims one task (no number: the next one) and prints its text, thread, links and the files it names; if it is refused, another session has it. Then `agentdrop task comment B<n> "…"` for notes, `task ask B<n> "<question>" --context "…" --option … --option … --pick <n>` for a question to the owner (the task then waits for them; the form is below), `task state B<n> waiting_others "<whom>: …"` when it waits for other people, `task new "…"` to file a task, and `task handin B<n>` when the work is committed, then `agentdrop accept B<n>`, which marks it done on a pass.

| File | What goes there |
|---|---|
| `docs/CONTEXT.md` | product, people, data sources, glossary, code map; changes rarely |
| `docs/DECISIONS.md` | only choices a named human made between alternatives, costly to forget: what, why, rejected, what not to undo, last line `Decided: who, where, quote` (`check_docs.sh` checks it). Bugs, UI, ops, facts and agent defaults go to their own files; same day. Superseded entries move whole to `DECISIONS.archive.md` |
| `docs/CONVENTIONS.md` | rules we always follow |
| `docs/PITFALLS.md` | traps we already fell into |
| `docs/OPERATIONS.md` | run, deploy, servers, access; names and paths only, no secrets |
| `docs/STATE.md` | what works, half-done, broken; rewrite whole when the picture changes |
| `docs/TODO.md` | tickets `B<n>` with P0–P3 (now / next / later): only what remains and its source; done → `LOG.md`, history → spec; numbers never reused. A ticket that can start only when another is done says so in its first paragraph: `После: B12` / `After: B12`. `[автономно]` / `[autonomous]` after the code: an unattended run may do it; `[с человеком]` / `[with owner]`: only together with the owner |
| `docs/QUESTIONS.md` | questions for the owner or others; agent decisions the owner may revert; closed items kept a week, then deleted |
| `docs/LOG.md` | one 3–5 line entry per finished pass, newest on top |
| `docs/specs/B<n>-<name>.md` | spec for a multi-pass task; report appended at the end |
| `docs/research/` | reference studies; every number has a source and date |
| `docs/reviews/inbox/` | raw reviews and audits, any name; the `review-intake` skill (`.claude/skills/review-intake/SKILL.md`, other harnesses: read and follow it) merges duplicates, sets P0–P3 and files tickets after the owner's OK |
| `docs/archive/` | closed specs, processed reviews, outdated docs; `git mv` here, never edit |
| `LOCAL.md` | machine-specific notes, not in git |

Every markdown file lives in a place from this table or `.docs-allow`; `scripts/check_docs.sh` enforces it on commit.

**Threads in docs:** the owner comments under an item as `> **Name, dd.mm hh:mm:** …`. Answer under the comment in the same quote format, not only in chat; keep the thread until the item is archived; commit it with your pass. A thread ending in `_Thread closed._` (or `_Ветка закрыта._`) is resolved: in your next pass finish the item by the project's rules (move it to done, remove the ticket, log the decision).

**Acceptance:** when a ticket's work is done and committed, and before you remove it from `TODO.md`, run `agentdrop accept B<n>`. It runs the project's checks (`docs/checks`, one command per line), then a fresh judge who sees the ticket, its spec and the diff, never your report; it takes up to half an hour, so run it in the background. Exit 1: a check failed or the judge rejected, so fix what it printed and run it again. Exit 3: the ticket went to the owner (the third rejection, or the judge can't decide), so stop and wait for their answer under the ticket. Exit 0: accepted; finish the pass (the owner sees it on the board and in your pass-end brief).

**The morning session:** the owner may start a Claude Code session (a scheduled or hand-started task) that tidies the docs of projects nobody is working in: acts on the owner's answers, closes tickets that are already done, fixes stale ticket text. It holds the claim `TIDY` while it works; leave the docs alone while `agentdrop status` shows it.

**Finishing a pass:** entry in `LOG.md`; update `STATE.md` if the picture changed; remove the done ticket from `TODO.md`; `agentdrop release B<n>`. Commit only your own files, no AI attribution. Then the pass-end brief, below.

**Questions for the owner** (`QUESTIONS.md`, tickets waiting for an OK) are read on their own, out of context, often on a phone, so each one is asked in parts with `agentdrop task ask B<n>` (in a markdown project too: it writes the item into `QUESTIONS.md`): the question itself, one line of up to 120 characters; the context (`--context`), one line of up to 120 characters on what the task is for and where it stands now ("Moving the export to the new server: the code is ready, only the time is left"), so the owner doesn't lose the thread between questions; 2 to 4 options (`--option`, up to 60 characters each); your pick (`--pick`, a number or letter); and, if needed, `--details` of any length. File paths, ticket codes and the reasoning go only in the details, so the question and options read in five seconds and are answered by one tap. The question, the context and the options name things by what the owner sees on the screen or in the result ("the summary line at the top of Overview"), never by an internal name, a file, a function or another task's code: the owner has not read the code and does not remember what B41 was. A question about how something looks adds `--design` and its pictures, files inside the project: one `--pic` per option in the options' order, or a `--before` and `--after` pair that really differ, taken of the screen now and of how it will be. In a project with a design doc (`DESIGN.md` or `DESIGN_SYSTEM.md`) every question says which it is, `--design` with pictures or `--no-design`. `task ask` refuses a question without context or options, a line too long, a design question without pictures or, in a project with a design doc, a question that says neither, and says what to fix. A ticket waiting for an OK quotes its draft, numbers or options in the item itself, never "see CONVENTIONS.md" or a code without words.

**Pass-end brief:** your last message of a pass is a brief the owner can read on a phone without opening anything. (1) What happened, meaning first, the code in parentheses: "the mobile tooltip fix (B64) is live", never "B64 done". (2) The key number, or the draft itself, quoted inline. (3) What needs the owner: options with your pick. (4) What you will do if nobody answers. Link only rendered pages, never raw markdown files: in the owner's chat they open as a diff among dozens of files.

**Grill:** when the owner brings a new idea, a pasted brief or several asks that pull different ways, don't build from guesses: offer a grill in one line. The `grill` skill (`.claude/skills/grill/SKILL.md`, other harnesses: read and follow it) asks in rounds with your recommended answer, writes the glossary and decisions as answers land, and ends with a spec and proposed tickets.

**Harvest:** lessons that would help any project go up into the owner's agentdrop rules, not only into this project's docs. When five or more passes sit above the `<!-- harvest -->` marker in `LOG.md` (in Claude Code a SessionStart hook says so), or a pass produced a rule that isn't about this project, offer a harvest in one line; the `harvest` skill (`.claude/skills/harvest/SKILL.md`, other harnesses: read and follow it) proposes and writes after the owner's OK.
